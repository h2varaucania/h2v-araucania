\section{El sitio en una página}
% ════════════════════════════════════════════════════════════════

El sitio es \textbf{una sola aplicación} que contiene las páginas públicas y el panel de administración (\ruta{/admin}). El contenido que se edita en el panel se guarda en una base de datos; los archivos subidos (imágenes, PDF, capas KMZ), en un almacén de archivos; y el código, en GitHub. Cada cambio de código que llega a la rama principal de GitHub se publica solo.

\section{Cómo se publica un cambio de código}
% ════════════════════════════════════════════════════════════════

Cada vez que llega un cambio a la rama \var{main}, Vercel compila y publica solo, en unos 2 minutos. El comando de compilación está en \ruta{vercel.json}:

\begin{codigo}
TSX_TSCONFIG_PATH=./tsconfig.json npx payload migrate && npm run build
\end{codigo}

Es decir: primero aplica a la base de datos las migraciones pendientes y después compila. En paralelo, GitHub corre las pruebas automáticas (\ruta{.github/workflows/ci.yml}: revisión de estilo, tipos, pruebas unitarias y compilación). Vercel \textbf{no espera} a esas pruebas.

\textbf{Procedimiento recomendado para un cambio:}
\begin{pasos}
\item Sacar un respaldo: GitHub → \textbf{Actions} → ``Respaldo diario de la base de datos'' → \textbf{Run workflow}, y esperar que termine en verde.
\item Trabajar en una rama nueva y probar en local (sección~\ref{sec:local}).
\item Abrir un \emph{pull request}: las pruebas automáticas corren solas.
\item Unir a \var{main}. Vercel publica.
\item Revisar el sitio y el panel.
\end{pasos}

\begin{recuadro}{fondorojo}{h2vrojo}
\titulorecuadro{h2vrojo}{Cuidado con las vistas previas y la base de datos}
Como el comando de compilación aplica migraciones, una vista previa de Vercel (una rama que no es \var{main}) que tenga acceso a \var{DATABASE_URI} de producción \textbf{cambiaría la base de producción} con el código de una rama sin aprobar. Antes de usar ramas con vista previa, confirme en Vercel que \var{DATABASE_URI} solo esté en el entorno \textbf{Production}, o que en \textbf{Preview} apunte a una rama de prueba de Neon.
\end{recuadro}

\textbf{Volver atrás.} Si una publicación sale mal: Vercel → \textbf{Deployments} → la publicación anterior → \textbf{Instant Rollback}. En el plan gratuito solo se puede volver a la publicación inmediatamente anterior. Volver atrás \textbf{no deshace} los cambios que la migración ya hizo en la base de datos: para eso está el respaldo del paso 1.

\section{Base de datos y migraciones}
% ════════════════════════════════════════════════════════════════

El esquema de la base está versionado en \ruta{src/migrations/}: cada archivo es un cambio, en orden, y la tabla \var{payload_migrations} registra cuáles ya se aplicaron. Se aplican solas al publicar.

\textbf{Reglas:}
\begin{itemize}
\item Nunca cambiar el esquema de producción a mano ni con \var{PAYLOAD_DB_PUSH}. Todo cambio va en una migración.
\item Una migración nueva se genera y después se endurece a mano:
\end{itemize}
\begin{codigo}
set -a; source .env; set +a
TSX_TSCONFIG_PATH=./tsconfig.json npx payload migrate:create nombre_del_cambio
\end{codigo}
\begin{itemize}
\item Endurecer: \cmd{IF NOT EXISTS} en tablas, columnas e índices; tipos y restricciones dentro de \texttt{\detokenize{DO $$ ... EXCEPTION WHEN duplicate_object THEN null; END $$}}. Dejar el \var{down} vacío si borraría datos (ejemplo: \ruta{src/migrations/20260924_134519_mensajes_contacto.ts}).
\item Probarla contra una base vacía (todas las migraciones seguidas) y volver a correrla, para confirmar que se puede repetir sin error.
\end{itemize}

\textbf{Historia que conviene conocer.} La base de producción se creó en junio de 2026 con el modo automático de Payload (\emph{push}), antes de que existieran las migraciones. Por eso tiene algunas diferencias con una base creada solo con migraciones. La conocida (columnas obligatorias que impedían crear noticias) se corrigió con la migración \ruta{20260923_120000_borradores_aceptan_vacios}. Para reproducir fallas de producción, trabajar sobre una copia restaurada de un respaldo, no sobre una base nueva.

\begin{recuadro}{fondooro}{h2voro}
\titulorecuadro{h2vazul}{El punto débil: todo está en la misma cuenta}
El respaldo diario vive dentro de GitHub, en la misma cuenta que el código. Si se pierde el acceso a esa cuenta, se pierden también los respaldos. Por eso la rutina mensual incluye guardar una copia \textbf{fuera} de GitHub y de Vercel.
\end{recuadro}

\subsection{Rutina mensual (unos 15 minutos)}
\begin{pasos}
\item GitHub → \textbf{Actions}: confirmar que los respaldos diarios del mes terminaron en verde.
\item Abrir el respaldo más reciente → \textbf{Artifacts} → descargar el archivo y guardarlo en el almacenamiento institucional.
\item Respaldar los archivos subidos, desde la carpeta institucional donde se quiere dejar la copia:
\end{pasos}
\begin{codigo}
node scripts/respaldar-archivos.mjs https://h2v-araucania.vercel.app
\end{codigo}
\begin{pasos}[resume]
\item En el panel: revisar la lista de \textbf{Usuarios} (que no haya cuentas de personas que ya no están) y los \textbf{Mensajes de contacto} sin atender.
\end{pasos}

El script deja una carpeta \var{respaldo-archivos-AAAAMMDD/} con las imágenes, los PDF, las capas KMZ y un índice. Se puede repetir: no vuelve a bajar lo que ya está. Probado el 24-09-2026: 50 archivos (unos 85~MB con los tamaños reducidos de las imágenes) y 3 capas KMZ.

\textbf{Restaurar.} Los pasos están en \ruta{scripts/restore-db.md}. La restauración de la base está probada; la de los archivos está descrita, pero no probada.

\begin{recuadro}{fondorojo}{h2vrojo}
\titulorecuadro{h2vrojo}{Los respaldos contienen datos personales}
Correos y nombres de usuarios, las contraseñas cifradas y los mensajes del formulario de Contacto. Guárdelos en un lugar con acceso restringido y no los comparta. Desde el 1 de diciembre de 2026 rige la Ley 21.719 de protección de datos personales.
\end{recuadro}

\section{Dirección propia (dominio)}\label{sec:dominio}
% ════════════════════════════════════════════════════════════════

El dominio lo decide y lo registra \textbf{la institución, a su nombre}: un dominio \var{.cl} en NIC Chile con el RUT de la institución, o una dirección dentro de un dominio que ya tenga (por ejemplo, un subdominio de \var{energia.gob.cl}, que crea su área informática). Hoy \var{h2varaucania.cl} está registrado por un tercero y vence el 10-10-2026.

\textbf{Pasos, una vez decidido el dominio:}
\begin{pasos}
\item Vercel → proyecto → \textbf{Settings} → \textbf{Domains} → agregar el dominio. Vercel muestra los registros DNS exactos que hay que crear.
\item Crear esos registros en el DNS del dominio y esperar a que Vercel lo marque como válido.
\item Cambiar \var{NEXT_PUBLIC_SITE_URL} a la dirección nueva (con \var{https://}).
\item Si ya se quiere aparecer en Google: crear \var{SITE_INDEXABLE} con el valor \var{true}.
\item Resend → \textbf{Domains} → agregar el mismo dominio y crear en el DNS los registros que indica. Cuando Resend lo verifique, crear \var{EMAIL_FROM} con una dirección de ese dominio y, si corresponde, cambiar \var{CONTACT_EMAIL} a un correo institucional.
\item Volver a publicar (\textbf{Redeploy}).
\item Probar: \textbf{¿Olvidaste tu contraseña?} con un correo institucional debe llegar; un mensaje de prueba en Contacto debe quedar en el panel con ``Aviso por correo: Enviado''.
\end{pasos}

La dirección \url{https://h2v-araucania.vercel.app} sigue funcionando después. Vercel puede redirigirla al dominio nuevo (Settings → Domains).

\section{Mantención y seguridad}
% ════════════════════════════════════════════════════════════════

\subsection{Actualizar el software}
Next.js y Payload publican correcciones de seguridad con frecuencia. Un sitio que nadie actualiza acumula fallas conocidas.
\begin{itemize}
\item Activar las alertas de Dependabot en GitHub (repositorio → Settings → Code security → \textbf{Dependabot alerts}). Los avisos llegan al correo de la cuenta.
\item Cada tres meses, o ante un aviso de seguridad, en una rama nueva:
\end{itemize}
\begin{codigo}
npm outdated          # qué versiones nuevas hay
npm update            # Payload y @payloadcms/* a la última 3.x, juntos
npm install next@16   # Next.js va fijado: subirlo a la última 16.x
npm run lint && npx tsc --noEmit && npm test && npm run build
\end{codigo}
\begin{itemize}
\item Un cambio de versión mayor (Payload 4, Next.js 17) es un proyecto aparte: leer primero sus notas de migración. Probar siempre el panel en local antes de unir a \var{main}.
\end{itemize}

\subsection{Cómo está protegido}
\begin{tabularx}{\textwidth}{@{}P{3.8cm}Y@{}}
\toprule
\cab{Medida} & \cab{Detalle}\\
\midrule
\fila{Roles del panel} & Administrador (todo), Editor (publica, lee mensajes; no borra, no ve usuarios ni configuración). Solo Administradores crean cuentas y borran contenido.\\
\fila{Bloqueo de entrada} & 5 intentos fallidos bloquean la cuenta 10 minutos. El panel entra solo con correo y contraseña: exigir contraseñas largas.\\
\fila{Formulario de Contacto} & Máximo 5 mensajes cada 15 minutos por dirección IP. Los mensajes solo los leen Administradores y Editores; nadie puede crearlos por la API.\\
\fila{Cabeceras de seguridad} & Content-Security-Policy, Strict-Transport-Security, X-Frame-Options (DENY), Referrer-Policy y Permissions-Policy (\ruta{next.config.ts}).\\
\fila{Buscadores} & Mientras no exista \var{SITE_INDEXABLE}, el sitio pide a Google no indexarlo.\\
\bottomrule
\end{tabularx}

\subsection{Cuando una persona deja la institución}
\begin{itemize}
\item Eliminar su cuenta del panel o bajarle el rol el mismo día. Mantener siempre dos Administradores.
\item Si tenía acceso a la cuenta de Google o a GitHub: cambiar la contraseña, reemplazar su teléfono en la verificación en dos pasos y generar códigos de respaldo nuevos.
\item Si era Administrador y se fue en malos términos: cambiar \var{PAYLOAD_SECRET} y volver a publicar (cierra todas las sesiones).
\end{itemize}

\section{Trabajar en local}\label{sec:local}
% ════════════════════════════════════════════════════════════════

Requisitos: Node~22, Docker y git.
\begin{codigo}
git clone https://github.com/h2varaucania/h2v-araucania.git
cd h2v-araucania
cp .env.example .env            # valores locales, no los de producción
docker compose up -d postgres   # PostgreSQL local
npm ci
npm run dev                     # sitio y panel en http://localhost:3000
npm test                        # pruebas unitarias
\end{codigo}

Para probar como en producción: \cmd{npm run build} y luego \cmd{node .next/standalone/server.js}, después de copiar \ruta{public/} y \ruta{.next/static/} dentro de \ruta{.next/standalone/}. Las pruebas de extremo a extremo (\ruta{tests/e2e/}, Playwright) se corren con \cmd{npm run test:e2e} contra un servidor local; no forman parte de las pruebas automáticas de GitHub.

\textbf{Trampas conocidas:}
\begin{itemize}
\item La línea de comandos de Payload necesita \var{TSX_TSCONFIG_PATH=./tsconfig.json}. Los tipos se regeneran con \cmd{npm run payload:generate}, no con \cmd{payload generate:types}.
\item Los comandos no cargan \ruta{.env} solos: antes, \cmd{set -a; source .env; set +a}.
\item Con \var{NODE_ENV} distinto de \var{production}, Payload ``arregla'' en silencio el esquema de la base a la que se conecta. Para trabajar con una copia de producción: \cmd{NODE_ENV=production PAYLOAD_DB_PUSH=false}.
\item Si \var{payload_migrations} tiene una fila llamada \var{dev}, las migraciones piden confirmación: borrar esa fila en la base local.
\item El mapa de componentes del panel debe generarse con el almacén Blob activo. Lo hace solo, antes de cada compilación, el comando \cmd{npm run payload:importmap}. Si se genera sin él, el panel de producción queda en negro.
\item Para \var{pg_dump} se usa la conexión directa de Neon (sin \var{-pooler}).
\end{itemize}

\section{Llevar el sitio a otro servidor}\label{sec:mover}
% ════════════════════════════════════════════════════════════════

Si la institución prefiere alojarlo en sus servidores, el repositorio ya trae \ruta{Dockerfile} (Node~22, salida \texttt{standalone}) y \ruta{docker-compose.prod.yml} (aplicación y PostgreSQL). Es trabajo de un informático, del orden de uno a dos días:
\begin{pasos}
\item Crear un PostgreSQL 17 y restaurar el último respaldo (\ruta{scripts/restore-db.md}).
\item Archivos: sin \var{BLOB_READ_WRITE_TOKEN}, el sitio guarda las subidas en disco (\ruta{public/uploads/}, en un volumen persistente). Copiar ahí el contenido de \ruta{media/} y, en \ruta{public/uploads/capas-geo/}, el de \ruta{capas-geo/} del respaldo de archivos. Otra opción es seguir usando Vercel Blob con su token.
\item Configurar las variables de entorno (sección~\ref{sec:variables}), servir con HTTPS detrás de un proxy y aplicar las migraciones (\cmd{npx payload migrate}) antes de arrancar.
\item Apuntar el dominio al servidor nuevo y comprobar el panel, las subidas y el formulario de Contacto.
\end{pasos}
